# Feature Specification: Voice Level Indicator Scaling & Forced Response Language

**Feature Branch**: `014-voice-level-and-language`  
**Created**: 2026-05-28  
**Status**: Draft  
**Input**: User description: "Verborra 0.14 — two independent improvements bundled into one release. (1) The shared voice level indicator (today rendered as a thin bar in several places) must become visibly taller and scale relative to its container's height, with amplitude mapping tuned so that normal-volume speech produces a clearly visible deflection rather than barely moving the bar. (2) Response language: there is a persistent default value configured in Settings and a temporary, per-window override surfaced in the floating dictation window. The floating-window value must be forcibly applied to the message being submitted — including the very first message of the session. Mechanically, the existing dictation flow is two-stage: stage 1 transcribes the user's voice in their spoken (source) language; stage 2 formats the transcribed text via the LLM. The fix lives in stage 2: a translation directive must be appended to the formatting step of the form 'Return the text in the target language X — if the transcribed text is in another language, translate it; if it already matches the target language, leave it unchanged.' Both directions apply to macOS app Verborra."

## Overview

Release 0.14 addresses two unrelated but user-visible weaknesses in the current product. They are bundled into a single release because each is small and self-contained, but they should be treated as independent user stories — implementable, testable, and shippable independently. Direction 1 fixes a confidence problem in the dictation UI (users cannot tell whether the mic is actually picking them up). Direction 2 fixes a correctness problem (the temporary response-language override surfaced in the floating dictation window is not reliably applied to the first message of a session).

### Today's pipeline (background for Direction 2)

Verborra's dictation flow is already two-stage:

1. **Recognition (stage 1)** — the user's voice is transcribed in the source language they actually spoke. The output of this stage is plain transcribed text in the source language.
2. **Formatting (stage 2)** — the transcribed text is sent to the LLM together with a system prompt for cleanup/formatting. This is the stage that produces the final user-visible result.

Response language is split across two values today:

- **Default (persistent)** — configured in Settings. This is the value the app falls back to whenever there is no per-session override.
- **Override (temporary, per-window)** — surfaced in the floating dictation window's response-language selector. The user can switch this between turns; it is intended to apply to the next submission without permanently changing the Settings default.

The defect: the temporary override is not reliably honoured on the first message of a session. The fix in this spec is to make stage 2's formatting step explicitly carry a translation directive built from the resolved target language, so the override always wins for the message being submitted.

## Clarifications

### Session 2026-05-28

- Q: How does the floating-window response-language override relate to the Settings default — does it write back, persist per launch, or reset per window? → A: Per-window ephemeral. On each opening of the floating window the override is initialized from the current Settings default. The user may keep or change the override; this value is always passed to the formatting stage as the target language. Changes to the override never mutate the Settings default. Closing the floating window discards the override; the next opening re-initializes it from the Settings default again.
- Q: What happens if the LLM ignores the translation directive and returns output in a language other than the resolved target? → A: Accept the output as-is. The system MUST NOT perform post-hoc language detection, retry, or warn the user. Residual non-compliance is treated as a quality/monitoring concern (handled via prompt-engineering quality, not runtime control flow).
- Q: Does the translation directive apply to every submission, or only to the first message of a chat? → A: Only to the first voice-originated submission of a chat session — the one that carries the system prompt to the formatting stage. Subsequent voice turns in the same chat do NOT receive the directive; the conversation continues in whatever language the first turn established. Changing the floating-window override mid-chat does NOT retarget the current chat's subsequent turns; a new chat session is required to apply a new target language.
- Q: Should language resolution be logged via the existing diagnostic logging system (spec 007)? → A: Yes — emit one structured event per first voice turn of a chat session. Required fields: resolved target language, confirmation that the directive was injected, and the source of the override value (Settings default carried forward unchanged vs. user-changed in the floating window). No diagnostic events are emitted from the language-resolution path on follow-up voice turns.

### Session 2026-05-29 (post-verify QA + architectural rework)

Iterating against live LLM behaviour on `gpt-4.1-nano` surfaced gaps in the original prompt assembly. The decisions below land as a single batch.

- Q: Should the per-language localized strings for `TranslateToTargetInstruction` and `DoNotAnswerInstruction` be retained, or consolidated to English? → A: Consolidated to **English only**. Behavioural rules (don't answer, translate the output) are most reliably followed when phrased in English; target-language name is communicated by interpolating its English-language name (e.g. "Spanish", "Russian", "Japanese") rather than by rendering the whole directive in the target language. This removes the 10-locale `translations` dictionaries from both enums.
- Q: How should the base prompt locale be chosen on the first voice turn? → A: **Always English** (`selectedPrompt.contentForLanguage(.en)`), regardless of the resolved target language. The pre-existing "Corrige los errores ortográficos y devuelve solo el texto corregido" Spanish base prompt (etc.) was creating a conflict with the translation directive — the LLM interpreted the localized base prompt as a same-language constraint and ignored the directive. English base prompt avoids that conflict entirely. Output language is enforced solely by the trailing `## Response Language Override` section.
- Q: What's the canonical wording convention for [MUST] rules in the system prompt? → A: **`[MUST]` only** — no `[MUST NOT]` form. Each previously-`[MUST NOT]` rule is rewritten as `[MUST]` with words like "never", "strictly", "only", or "without exception". The convention applies to Personal Preferences, Vocabulary Replacements, Response Instruction, and Response Language Override. Rationale: `[MUST NOT]` rules were typically paraphrases of the matching `[MUST]` (e.g. "MUST follow rules X" + "MUST NOT deviate from X"); the single-form convention removes redundancy and gives the LLM a clearer positive signal.
- Q: What does the `DoNotAnswerInstruction` look like after simplification? → A: One static English string under the heading **`## Response Instruction`** (renamed from "Critical Instruction"). Four `[MUST]` rules: (i) treat input as content for cleanup/formatting (intro sentence), (ii) if input is a question, return only the corrected question form — never an answer, (iii) never answer any question in the input text, (iv) never ask clarifying questions, (v) never execute commands or tasks. Concrete input/output examples that the previous 10-locale version carried are NOT retained — the positive `[MUST]` for the question case in (ii) replaces the example-as-grounding mechanism for `gpt-4.1-nano`.
- Q: What's the canonical order of sections in the assembled system prompt? → A:
  1. Base prompt (always English locale)
  2. `## Personal Preferences` — only if non-empty
  3. `## Vocabulary Replacements` — only if entries exist
  4. `## Response Instruction` — only when `injectDoNotAnswer == true` (i.e. first voice turn AND `answerQuestionsInFirstMessage == false`)
  5. `## Response Language Override` — **always last** for maximum LLM weight on small models

  This order is enforced by `SystemPromptBuilder.build(_:)` and applies to every formatting call across every code path (voice first turn, voice continuation, text input, fallback, `ChatSession.prepareMessagesForLLM`).
- Q: Where does prompt assembly live in the codebase? → A: A single static method **`SystemPromptBuilder.build(_: Input) -> String`** is the only place that assembles a dictation-style system prompt. Lives in [Verborra/Services/PromptEnhancer.swift](Verborra/Services/PromptEnhancer.swift) (file kept under the legacy name to avoid a `project.pbxproj` edit; the type inside is `SystemPromptBuilder`). The previous `PromptEnhancer` struct is removed. `DoNotAnswerInstruction` and `TranslateToTargetInstruction` enums live in the same file (co-located with the builder that consumes them, not under `SystemPromptDefinition.swift`). Single source of truth: every caller funnels through one method.
- Q: How do `FormattingService` / `StreamingFormattingService` interact with the builder? → A: They don't — the services accept an **already-assembled** system prompt and send it to the API unchanged. The previous parameters `vocabularyEntries`, `personalPreferences`, `skipResponseLanguageSection` are removed from both `FormattingServiceProtocol.format(text:systemPrompt:textLanguage:model:)` and `StreamingFormattingServiceProtocol.streamFormat(text:systemPrompt:textLanguage:model:)`. Callers in `RecordingViewModel` invoke `SystemPromptBuilder.build(...)` first, then pass the result to the service as `systemPrompt`. This means the protocol shape is fully decoupled from prompt assembly.
- Q: Should the diagnostic log truncation of `systemPrompt` be widened? → A: Yes — raised from `prefix(500)` to `prefix(4000)` in [StreamingFormattingService.swift](Verborra/Services/StreamingFormattingService.swift). With the new larger prompt (base + four sections), 500 chars only showed up to ~Vocabulary table; the tail-positioned `Response Language Override` was invisible to the log, making "did the directive get injected?" untriagable from logs alone. 4000 chars covers the full typical prompt without flooding the file (still bounded).
- Q: The 0.14 fix targets `gpt-4.1-nano` compliance — does the spec acknowledge model-specific brittleness? → A: Yes. `gpt-4.1-nano` is the active "small" model and is the binding constraint for prompt design. The decisions above (English-only directives, [MUST]-only convention, late-positioned Response Language Override, positive `[MUST]` for question-case) are all aimed at compensating for this model's weak instruction-following. If the project later migrates to a larger model, these mitigations can be reviewed (likely retained as defense-in-depth, since they don't harm larger models).

### Session 2026-05-29 (post-hotfix: `answerQuestionsInFirstMessage` toggle and language propagation)

User reported that the `answerQuestionsInFirstMessage` toggle had no observable effect on the built-in prompt and that switching language in the floating window during a chat session did not retarget continuation turns. Root-causing surfaced four distinct defects landed as a single batch on 2026-05-29.

- Q: Why did the `answerQuestionsInFirstMessage` toggle have no effect when the user enabled it on the built-in prompt? → A: Three independent gates silently no-oped the change: (i) [Views/SettingsView.swift:310](Verborra/Views/SettingsView.swift#L310) disabled the toggle with `.disabled(isReadOnly)` for the built-in prompt; (ii) [ViewModels/SettingsViewModel.swift:152](Verborra/ViewModels/SettingsViewModel.swift#L152) early-returned from `saveCurrentPrompt()` for read-only prompts; (iii) [Services/PromptsStore.swift:162](Verborra/Services/PromptsStore.swift#L162) rejected updates to read-only prompts. **Decision:** the read-only protection (FR-009b) covers `name`/`content` only — `answerQuestionsInFirstMessage` is a behavioural preference and is user-settable on every prompt, including the built-in `simple-voice-to-text` one. `PromptsStore.setAnswerInFirstMessage(promptID:value:)` bypasses the `isReadOnly` guard for this single field; the UI toggle is no longer `.disabled` and auto-persists on change for read-only prompts (no Save button is rendered for them).
- Q: Even after the toggle persists, why did the model still echo the input verbatim instead of answering a dictated question? → A: The trailing `## Response Language Override` directive included a second `[MUST]` rule — *"If the input is in a language other than `<TARGET>`, translate the meaning into `<TARGET>` and return only the `<TARGET>` translation"* — which the LLM interpreted as "echo the input translated, do not produce a substantive response." This wording is correct for echo/dictation mode but actively forbids answering. **Decision:** `TranslateToTargetInstruction` becomes two-branch via a new `allowAnswering: Bool` parameter. When `allowAnswering == true` (i.e. the toggle is ON, or the call is a chat continuation), only the first bullet (*"[MUST] Return the response text in `<TARGET>`"*) is emitted — the directive stays a pure output-language constraint. When `allowAnswering == false` (echo mode), both bullets are emitted as before. The builder derives `allowAnswering` as `!input.injectDoNotAnswer`. This amends FR-011 — see the FR-011 entry for the conditional shape.
- Q: With the language directive neutered for answer mode, the model still defaulted to echoing because the **base prompt itself** ("Fix spelling errors and add punctuation. Return only the corrected text.") dominates and locks the model into editor behaviour. How is this resolved? → A: Symmetric to `DoNotAnswerInstruction`: introduce `AnswerQuestionInstruction` — one English `[MUST]` rule, *"If the input text contains a question from the user, answer the question directly instead of cleaning it up or returning it"* — injected at the same Response Instruction position when the toggle is ON. The toggle now flips between two well-worded, clearly opposite directives instead of merely removing one. See new **FR-023**.
- Q: How does the assembled prompt's section 4 ("Response Instruction") change in section-order terms? → A: Section 4 is still conditional but now exactly one of two enums fires — never both, never neither (for first voice turns). Toggle OFF → `DoNotAnswerInstruction` (existing four `[MUST]` rules). Toggle ON → `AnswerQuestionInstruction` (single `[MUST]` rule). Continuation turns are unaffected (no section 4). The builder enforces mutual exclusion by checking `injectDoNotAnswer` first; `injectAnswerQuestion` only applies in the `else if` branch.
- Q: Why did switching the floating-window text language during an active chat session not retarget continuation turns? → A: `chatSession.textLanguage` and `chatSession.voiceLanguage` were captured at session creation and never updated. `RecordingViewModel.changeTextLanguage(_:)` mutated `selectedTextLanguage` (used on the first voice turn directly) but did not mirror the new value into the session. Continuation turns go through `ChatSession.prepareMessagesForLLM`, which reads `session.textLanguage` ([Models/ChatSession.swift:110](Verborra/Models/ChatSession.swift#L110)) → the old language was used. **Decision:** `changeTextLanguage(_:)` and `changeVoiceLanguage(_:)` now write through to `chatSession?.textLanguage` / `voiceLanguage`. This is a propagation fix only — FR-012 / FR-012a (the directive is NOT re-injected on continuation turns) is preserved. Continuation simply uses the current value for the language constraint.
- Q: Built-in prompt naming was inconsistent across locales (English had "Simple Voice To Text" while others were "Voice/Speech to Text" variants) — should the brand be aligned? → A: Yes. English renamed to **"Speech To Text"**; locales that distinguish "Voice" from "Speech" lexically are updated to use the Speech-side noun (es: Voz→Habla, fr: Voix→Parole, pt: Voz→Fala, it: Voce→Parlato). Locales whose standard tech idiom uses the voice-side noun (ru, de, zh, ja, ko) are unchanged. The stored `prompts.json` `name` field is otherwise frozen at install time, so a v3→v4 migration is added in [Services/PromptsStore.swift](Verborra/Services/PromptsStore.swift) to re-sync `name` and `content` for every system prompt from `SystemPromptRegistry` on next launch (safe to overwrite — system prompts are read-only and cannot diverge from the registry).
- Q: Log line `"directiveInjected":"true"` ([RecordingViewModel.swift:648](Verborra/ViewModels/RecordingViewModel.swift#L648)) is hardcoded — does this misreport when the answer-mode branch is taken? → A: No. The metadata refers to the `## Response Language Override` directive (always emitted) per FR-022, NOT the `## Response Instruction` block. The field remains accurate after the hotfix; documenting this here so future readers don't mistake it for a regression.

### Session 2026-05-29 (post-hotfix continued: OpenAI model compatibility and catalog updates)

After the toggle/language hotfix landed, manual testing across LLM models exposed that several picker entries fail at request time. Root-causing produced the further amendments below.

- Q: Why did `gpt-5-nano` and `gpt-5-mini` return HTTP 400 from OpenAI when every other model on the picker worked? → A: They are reasoning-tier models and reject any `temperature` other than the default `1`. The Verborra Chat Completions request hardcoded `"temperature": 0.2`, which OpenAI explicitly rejects with body `{"error":{"message":"Unsupported value: 'temperature' does not support 0.2 with this model. Only the default (1) value is supported.","type":"invalid_request_error","param":"temperature","code":"unsupported_value"}}`. Confirmed against production log `verborra-2026-05-29T13.jsonl`. **Decision:** introduce `LLMModel.supportsTemperature: Bool` ([Verborra/Models/LLMModel.swift](Verborra/Models/LLMModel.swift)). `false` for `gpt-5-nano`, `gpt-5-mini`, `gpt-5.4-nano`, `gpt-5.4-mini` (reasoning-tier convention). `true` for everything else. Both request builders (`StreamingFormattingService.buildRequest`, `FormattingService.format`) omit the `temperature` key from the request body entirely when the property is `false`. Sending `1.0` explicitly also works but omission is safer if OpenAI tightens the rule further.
- Q: Why couldn't this be diagnosed from the log alone? → A: The streaming service only logged the HTTP status code (`"status": "400"`) on non-200, never the response body. OpenAI's actual error message lived in the body — without capturing it, root-causing required hypothesis-testing against the live API. **Decision:** capture the response body on every non-200 in both [StreamingFormattingService.swift](Verborra/Services/StreamingFormattingService.swift) and the non-streaming [FormattingService.swift](Verborra/Services/FormattingService.swift). Capped at 2000 chars for 401 / 4xx, 4000 chars for streaming non-200 ("body" parameter on the ERROR log line). New helper `StreamingFormattingService.collectBody(_:cap:)` drains the byte stream into a UTF-8 string. The streaming `Streaming request details` DEBUG line also reports `"temperature": "omitted"` when the key was dropped, so the log reflects the actual request shape rather than a hardcoded value.
- Q: Should the default LLM model change? → A: Yes — from `gpt-4.1-nano` to `gpt-5.1` ([Verborra/Models/LLMModel.swift](Verborra/Models/LLMModel.swift)). Rationale: (a) GPT-5.1 ships at $1.25 input / $10 output per 1M tokens, comparable to the nano tier on cost per typical dictation message (~100 input tokens, ~100 output tokens ≈ ~$0.001/message vs nano's ~$0.00005); (b) the dictation+format flow now also serves chat continuation and answer-mode (post-014 hotfix), where 5.1's quality margin matters more than the marginal cost; (c) existing installs are unaffected — they keep their persisted `selectedLLMModelRawValue` via `@AppStorage`.
- Q: How are the picker entries themselves managed? → A: `LLMModel` is a hand-maintained `enum: String, CaseIterable`. Each case lists: the OpenAI identifier string (rawValue), a display name, an English `model.llm.<id>.info` description with inline pricing, and a Russian translation. Adding a model requires updating six places: enum case, `displayName` switch, `infoDescription` switch, `supportsTemperature` switch, `TokenEstimator.contextLimit(for:)`, and two `Localizable.xcstrings` entries. **Decision:** keep this hand-maintained — model add/remove is rare and explicit; introducing a config-file source-of-truth would over-engineer for the current velocity. The trade-off is documented here so future maintainers don't expand the abstraction prematurely.
- Q: Catalog hygiene — what should be in the picker right now? → A: 12 models as of 2026-05-29 (after removing `gpt-4.1-nano` and `gpt-5.3`). Removals: `gpt-4.1-nano` (OpenAI marked deprecated, "Not recommended for new projects"); `gpt-5.3` (returns 404 — identifier doesn't exist at OpenAI). Additions (6, all from OpenAI's flagship table): `gpt-5.5`, `gpt-5.5-pro`, `gpt-5.4`, `gpt-5.4-mini`, `gpt-5.4-nano`, `gpt-5.4-pro`. Existing installs with `selectedLLMModelRawValue` matching a removed case fall back silently to `LLMModel.default = .gpt51` via the `?? .default` clause in [AppSettings.swift:168](Verborra/Models/AppSettings.swift#L168). No migration needed.
- Q: `gpt-5.4-mini` and `gpt-5.4-nano` are marked `supportsTemperature = false` without live confirmation — is this safe? → A: It's a heuristic, applied by analogy from `gpt-5-mini` / `gpt-5-nano`. OpenAI's pattern across the GPT-5 family is that `*-mini` and `*-nano` variants are reasoning-tier and require `temperature: 1`; flagship and `*-pro` accept arbitrary values. The new body-logging means the first failed call will surface the exact error in the log if the heuristic is wrong; flipping the boolean to match reality is a one-line change. Documenting the heuristic here so the assumption is reviewable.
- Q: Latent: when the non-streaming fallback ([FormattingService.performWithRetry](Verborra/Services/FormattingService.swift)) hits 400, the loop continues and retries the same 400-bound request three times. Is this in scope? → A: **Out of scope for this batch — tracked as a known issue.** The `catch let error as RecordingError` clause stores the thrown error in `lastError` and falls through to the next iteration, so 4xx (which should NOT be retried) is retried up to `maxRetries` times. This is wasted requests but does not change the outcome (still fails after N attempts). The fix is to re-throw immediately on non-`apiKeyNotConfigured` `RecordingError.formattingFailed`; deferred to a follow-up rather than bundled into this hotfix.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Floating-window response language override is forcibly applied on the first voice turn of a chat session (Priority: P1)

A user opens the floating dictation window with a default response language already configured in Settings (e.g. English). Before submitting their first message, they change the response language in the floating window to French — they want this one chat session to come out in French without permanently changing their Settings default. They dictate in any source language and submit the first voice turn. They expect — and require — the resulting message to be in French. Today this fails on the first voice turn: the override is not reliably honoured and the result often comes back in the source language or the previous default. The translation directive that fixes this is injected only on the first voice turn of a chat session — subsequent turns of the same chat continue in the language established by the first turn (existing chat-continuation behavior).

**Why this priority**: This is a correctness defect, not polish. The user has explicitly stated this is a mandatory requirement. When the floating window exposes a response-language selector specifically so users can override the default per session, that override must actually take effect — and it must take effect on the first submission, which is the precise case that fails today. Failing this undermines trust in the entire response-language feature.

**Independent Test**: Can be fully tested by configuring one default in Settings, opening the floating window, switching the floating-window response language to a different value, dictating a single message in any source language, submitting it, and verifying that the resulting formatted message is in the floating-window-selected language. Requires no changes to the voice indicator to validate.

**Acceptance Scenarios**:

1. **Given** the Settings default response language is English and the floating window's override is set to French *before* any message is submitted, **When** the user dictates their very first message of the session in Russian (or any other source language) and submits it, **Then** the final formatted message is produced in French.
2. **Given** the Settings default response language is English and the floating window's override is also English, **When** the user dictates a message in English and submits it, **Then** the formatted message remains in English and is not unnecessarily rewritten or translated.
3. **Given** the Settings default response language is English and the floating-window override is set to French, **When** the user dictates a message that is already in French and submits it, **Then** the formatted message is in French and is not retranslated (the directive's "if it already matches, leave unchanged" branch applies).
4. **Given** the user has already submitted the first voice turn of a chat session in French and received a French response, **When** they dictate one or more follow-up voice turns within the same chat session, **Then** the follow-up responses continue to be produced in French — no translation directive is re-injected, and the language is established by the first turn.
4a. **Given** the user has submitted the first voice turn of a chat session in French, **When** they change the floating-window override to German *mid-chat* and submit another voice turn within the same chat, **Then** the follow-up still continues in the established language (French). To produce a chat targeted at German, the user must start a new chat session (e.g. by closing and reopening the floating window).
5. **Given** the user changes the Settings default response language, **When** they next open the floating window, **Then** the floating window's override is initialized from the new Settings default. Conversely, changes the user makes to the override inside the floating window are scoped to that open window only and never mutate the Settings default. Closing the window discards the override; the next opening re-initializes it from the Settings default again.
6. **Given** the user closes the floating window after a chat session, then reopens it and changes the override to a new language *before* dictating, **When** they submit the first voice turn of this newly opened chat session, **Then** the response is produced in the new language (because reopening starts a fresh chat session and the new first turn carries the directive).

### User Story 2 — Voice level indicator is visibly responsive at normal speaking volume (Priority: P2)

A user starts recording (in the floating dictation window or any other view that embeds the voice level indicator) and speaks at a normal, conversational volume. They expect the indicator to clearly move in response to their voice — enough to give immediate confidence that the microphone is picking them up. Today the indicator is a thin horizontal line that barely deflects unless the user speaks loudly, leaving users unsure whether anything is being captured.

**Why this priority**: This is a UX/confidence issue, not a correctness defect — dictation still works. But it directly affects perceived reliability of the most important interaction in the product. Lower priority than US1 only because it does not change *what* the product produces, only how visibly it shows what it is doing.

**Independent Test**: Can be fully tested by opening any view containing the indicator, speaking at normal volume, and visually verifying that the deflection clearly fills a substantial portion of the indicator's container height. Requires no changes to the language behaviour to validate.

**Acceptance Scenarios**:

1. **Given** the floating dictation window is showing the voice level indicator, **When** the user speaks at a normal, conversational volume, **Then** the indicator's deflection clearly and continuously fills a substantial portion of its container's available height (not a thin sliver).
2. **Given** the indicator is embedded in a container with a small height budget, **When** the user speaks, **Then** the indicator scales its rendered amplitude to that smaller container so it still looks "full enough" without overflowing.
3. **Given** the same indicator is embedded in a container with a larger height budget, **When** the user speaks at the same volume, **Then** the rendered amplitude scales up to use more of that larger height budget — the indicator never feels disproportionately small for its container.
4. **Given** the room is silent, **When** the indicator is rendered, **Then** it shows a clearly distinguishable "silence" baseline (small or no deflection), so the user can tell silence apart from speech.
5. **Given** the user speaks loudly, **When** the indicator renders, **Then** the deflection saturates smoothly at the container's bound without clipping outside the container or causing visual artifacts.
6. **Given** the user transitions from silence to speech, **When** the indicator updates, **Then** the change is visually smooth (no flicker, no jitter) and feels immediate.

### Edge Cases

**Voice level indicator:**

- The microphone is unavailable or permission has been revoked: the indicator should render in a clearly inert state (e.g. flat silence baseline), not a misleading "active" state.
- Extremely loud audio (e.g. a cough or a loud burst): the rendered amplitude must remain bounded by the container's height; it must not overflow or clip outside.
- A very short utterance (a fraction of a second): the indicator must still show a visible deflection rather than missing it entirely due to smoothing.
- Container with a degenerate height (e.g. constrained to a few pixels): the indicator must degrade gracefully rather than produce visual artifacts.
- The indicator is embedded in a new view in the future: it must continue to adapt to the new container without per-call configuration.

**Forced response language:**

- The user changes the floating-window override mid-stream of an in-flight response: the in-flight response continues in its previous target language. The override change does not retroactively retarget the current chat — see next bullet.
- The user changes the floating-window override mid-chat (after the first voice turn of the chat session has already been formatted): subsequent voice turns of the same chat continue in the language established by the first turn. The override change does NOT re-inject the translation directive on follow-up turns. To apply a new target language, the user must start a new chat session (typically by closing and reopening the floating window).
- The user changes the floating-window override repeatedly before submitting the first voice turn: only the value present at submission of the first turn matters; that value becomes the resolved target for the chat session.
- The user has never dictated anything yet (fresh window) and changes the floating-window override: the upcoming first voice turn of the chat uses the new value.
- The user changes the Settings default while the floating window is already open: the open window's override is **not** retroactively updated. The new Settings default takes effect on the next opening of the floating window (per FR-013).
- The user closes and immediately reopens the floating window after changing the override: the override is discarded on close and re-initialized from the Settings default on reopen (i.e. the user's change is gone — this is the intended ephemeral behavior).
- The transcribed text (output of stage 1) is in a language not in the supported response-language set: the directive still asks for the resolved target language; if no faithful translation is feasible the formatting stage may produce best-effort output (see Assumptions).
- The transcribed text is in a mix of languages: the directive still requests the resolved target language; mixed-language input must be normalized to the target.
- The transcribed text already matches the target language: the directive's "leave unchanged" branch applies and the formatting stage performs cleanup only, not translation.
- The LLM ignores the directive and returns output in a language other than the resolved target: the output is accepted as-is. No detection, no retry, no user-facing warning. (See FR-021 and Out of Scope.)
- The Settings default is persisted across app restarts (existing behaviour, not regressed). The floating-window override is never persisted to disk — it lives only for the lifetime of an open floating window.

## Requirements *(mandatory)*

### Functional Requirements

**Voice level indicator (Direction 1):**

- **FR-001**: The voice level indicator MUST be rendered as a single shared component, reusable across all embedding locations, with no per-call duplication of logic.
- **FR-002**: The indicator MUST adapt its rendered amplitude to the height of its containing parent so that it visually "fills" the container appropriately, in both taller and shorter embedding contexts.
- **FR-003**: At a normal conversational speaking volume, the indicator's deflection MUST clearly fill a substantial portion of its container's available height — defined as at least 50% of available height at typical conversational input level (see Assumptions).
- **FR-004**: The indicator MUST visibly distinguish silence from speech: silence produces a small or zero baseline; speech produces a clearly larger deflection.
- **FR-005**: The indicator's rendered amplitude MUST be bounded by the container's height — loud audio MUST saturate smoothly at the container's edge and MUST NOT overflow outside the container.
- **FR-006**: The indicator's motion MUST be visually smooth — no flicker, no jitter, no perceptible step artifacts — across the silence-to-speech transition and during sustained speech.
- **FR-007**: The indicator MUST respond to the start of speech within a perceptually immediate timeframe (target: under ~100 ms from speech onset to visible deflection — see Success Criteria).
- **FR-008**: The indicator MUST continue to work in every location where it is currently used. Each call site MUST provide an explicit `.frame(height:)` to size the component to its role (see Clarifications 2026-05-29). Beyond this single layout modifier, no other per-call-site change is required.

**Forced response language (Direction 2):**

The dictation flow is treated as two stages: stage 1 (recognition) transcribes the user's voice in whatever source language they spoke; stage 2 (formatting) produces the final user-visible message. All language enforcement in this feature happens at stage 2.

- **FR-009**: At submission time, the system MUST resolve the **target language** for the message being submitted as the current value of the floating-window override. The floating-window override is always populated (see FR-013) and is therefore always the authoritative target.
- **FR-010**: Stage 1 (recognition) MUST continue to transcribe the user's audio in the actual source language they spoke. Stage 1 MUST NOT be biased toward the resolved target language. (Recognition fidelity to the spoken language is preserved.)
- **FR-011**: Stage 2 (formatting) MUST include an explicit `## Response Language Override` directive — built from the resolved target language — at the **end** of the system prompt for every submission that goes through the formatting stage. The directive is English with the target-language name interpolated. The directive is **two-branch** based on whether the model is permitted to produce a substantive response on this turn (see Session 2026-05-29 post-hotfix clarifications):
  - **Echo mode** (toggle OFF on first voice turn): two `[MUST]` rules — "(i) Return the response text in `<TARGET>`. (ii) If the input is in a language other than `<TARGET>`, translate the meaning into `<TARGET>` and return only the `<TARGET>` translation."
  - **Answer mode** (toggle ON on first voice turn; all chat-continuation turns): single `[MUST]` rule — "Return the response text in `<TARGET>`." The translate-and-return-only-translation rule is dropped because it semantically forbids producing a substantive response.

  Branch selection is `allowAnswering = !injectDoNotAnswer` in `SystemPromptBuilder` ([Verborra/Services/PromptEnhancer.swift](Verborra/Services/PromptEnhancer.swift)). Continuation turns always pass `allowAnswering: true` (see [Models/ChatSession.swift:110](Verborra/Models/ChatSession.swift#L110)).
- **FR-012**: Subsequent voice turns within the same chat session MUST NOT receive the translation directive. The conversation continues in whatever language was established by the first turn; this is the existing chat-continuation behavior and is preserved.
- **FR-012a**: A change to the floating-window override partway through an active chat session MUST NOT retarget the current chat's subsequent turns. To apply a new target language, the user must start a new chat session (e.g. by closing and reopening the floating window, which also reinitializes the override per FR-013).
- **FR-013**: On every opening of the floating dictation window, the floating-window override MUST be initialized from the current Settings default. The override starts each window session at "= Settings default" and can then be changed by the user.
- **FR-014**: Changes the user makes to the floating-window override MUST NOT mutate the Settings default. The Settings default is only changed via the Settings screen.
- **FR-015**: On closing the floating dictation window, the floating-window override MUST be discarded. On the next opening of the window, the override is re-initialized per FR-013 from the (possibly updated) Settings default.
- **FR-016**: A change to the floating-window override MUST take effect for the next **new chat session** initiated from that floating-window instance — not for subsequent turns of an already-started chat (per FR-012a). A change to the Settings default MUST take effect for the next *opening* of the floating window (via FR-013), and does not retroactively alter an already-open floating window's override. Mid-flight responses MAY continue in their previously resolved target language.
- **FR-017**: The Settings default MUST persist across app restarts (existing behaviour preserved).
- **FR-018**: When the input transcribed text already matches the resolved target language, the directive's "leave unchanged" branch MUST apply and the formatting stage MUST NOT unnecessarily retranslate or rephrase across languages (cleanup/formatting in the same language is permitted).
- **FR-019**: When the input transcribed text is in a different language from the resolved target language, the formatting stage MUST translate it into the resolved target language as part of producing the final output.
- **FR-020**: The set of supported target languages is unchanged from today's set (see Out of Scope).
- **FR-021**: The system MUST NOT perform post-hoc language detection on the formatting stage's output. The output is accepted as-is, regardless of whether it matches the resolved target language. No retry, no user-facing warning, no automatic correction is triggered on a language mismatch.
- **FR-022**: On the first voice turn of a chat session, the system MUST emit one structured diagnostic log event via the existing diagnostic logging system. The event MUST include: (a) the resolved target language, (b) confirmation that the translation directive was injected into the formatting stage, and (c) the source of the override value — either "settings-default" (the user did not change the override since the floating window opened) or "user-changed" (the user changed the override in the floating window before submitting). No diagnostic event is emitted from the language-resolution path on follow-up voice turns of the same chat session.

- **FR-023** (added 2026-05-29 post-hotfix): On the **first voice turn** of a chat session, the system MUST inject exactly one of two mutually-exclusive behavioural directives at the canonical section-4 position (`## Response Instruction`), based on the active prompt's `answerQuestionsInFirstMessage` toggle:
  - Toggle **OFF** → `DoNotAnswerInstruction` (four `[MUST]` rules — current behaviour, see Session 2026-05-29 post-verify QA clarifications).
  - Toggle **ON** → `AnswerQuestionInstruction` — one `[MUST]` rule: *"If the input text contains a question from the user, answer the question directly instead of cleaning it up or returning it."*

  Continuation turns MUST NOT receive either directive — they go through the chat-mode system message (`"You are a helpful assistant."` + Response Language Override only). Mutual exclusion is enforced by `SystemPromptBuilder.build(_:)`: `injectDoNotAnswer` is checked first; `injectAnswerQuestion` is the `else if` branch. The toggle MUST be user-settable on every prompt, including the read-only built-in `simple-voice-to-text` prompt (FR-009b's read-only protection covers `name`/`content` only — `answerQuestionsInFirstMessage` is a behavioural preference). The persistence path bypasses the read-only `updatePrompt` gate via `PromptsStore.setAnswerInFirstMessage(promptID:value:)`.

- **FR-024** (added 2026-05-29 post-hotfix): Changes to the floating-window text language (`RecordingViewModel.changeTextLanguage(_:)`) and voice language (`changeVoiceLanguage(_:)`) during an active chat session MUST be mirrored into `chatSession.textLanguage` / `chatSession.voiceLanguage`. This is a propagation requirement only — FR-012 (no re-injection of the translation directive on continuation turns) and FR-012a (mid-chat override change does NOT retarget the chat's directive-injected behaviour) are preserved. The mirroring ensures that the Response Language Override section assembled for continuation turns in `ChatSession.prepareMessagesForLLM` uses the user's current selection rather than the value captured at session creation.

- **FR-025** (added 2026-05-29 model-compat): On every non-200 HTTP response from the OpenAI Chat Completions endpoint, the diagnostic logging system MUST capture the response body verbatim into a `body` parameter on the ERROR log line. The body MUST be capped (4000 chars for streaming non-200; 2000 chars for 401 and non-streaming 4xx) to avoid log flooding. Helper `StreamingFormattingService.collectBody(_:cap:)` performs the streaming-body drain. Rationale: OpenAI error messages (e.g. `Unsupported value: 'temperature' does not support 0.2 with this model.`) are essential to root-cause 400/422 model-config errors; the status code alone is insufficient. The non-streaming `Streaming request details` DEBUG log MUST reflect the actual request shape — `"temperature": "omitted"` when the key was dropped per FR-026.

- **FR-026** (added 2026-05-29 model-compat): The `LLMModel` enum MUST expose a `supportsTemperature: Bool` property. Both Chat Completions request builders (`StreamingFormattingService.buildRequest` and `FormattingService.format`'s `requestBody`) MUST omit the `temperature` key entirely from the JSON body when this property is `false`. Currently `false` for `gpt-5-nano`, `gpt-5-mini`, `gpt-5.4-nano`, `gpt-5.4-mini` (OpenAI reasoning tier — accepts only the default value of 1; rejects any other with HTTP 400 `unsupported_value`). `true` for all flagship and `*-pro` variants. The classification is a hand-maintained heuristic; the body-logging mechanism (FR-025) makes a wrong classification self-diagnosing on the first failed request.

- **FR-027** (added 2026-05-29 model-compat): The `LLMModel.default` SHOULD be `.gpt51` (`"gpt-5.1"`) — not the historical `.gpt41Nano`. Rationale: (a) GPT-5.1 is cost-competitive for typical dictation message sizes; (b) post-014 the same pipeline serves answer-mode and chat continuation, where quality margin matters; (c) GPT-5.1 accepts arbitrary `temperature` so the default works regardless of the FR-026 classification. The default only fires for fresh installs (no `selectedLLMModelRawValue` in `UserDefaults`) and for the `LLMServiceProtocol.process(text:systemPrompt:)` convenience method — existing installs keep their persisted choice.

- **FR-028** (added 2026-05-29 model-compat): The `LLMModel` enum MUST track the OpenAI catalog. Removals MUST cover (a) models OpenAI deprecates ("Not recommended for new projects" — currently `gpt-4.1-nano`) and (b) identifiers OpenAI does not serve at all (404 — currently `gpt-5.3`). Additions track OpenAI's flagship-tier releases. As of 2026-05-29 the catalog is: `gpt-4o-mini`, `gpt-4.1-mini`, `gpt-5-nano`, `gpt-5-mini`, `gpt-5.1`, `gpt-5.2`, `gpt-5.4-nano`, `gpt-5.4-mini`, `gpt-5.4`, `gpt-5.4-pro`, `gpt-5.5`, `gpt-5.5-pro` (12 cases). Catalog churn MUST be reflected in six places per case: enum, `displayName`, `infoDescription`, `supportsTemperature` (FR-026), `TokenEstimator.contextLimit(for:)`, and two `Localizable.xcstrings` entries (`en` + `ru`). When a model is removed, existing installs with a matching persisted `selectedLLMModelRawValue` MUST fall back silently to `LLMModel.default` via the existing `?? .default` clause — no explicit migration is needed.

## Success Criteria *(mandatory)*

### Measurable Outcomes

**Voice level indicator:**

- **SC-001**: At a normal conversational speaking volume, the indicator's deflection visibly fills at least 50% of the available container height, in every place the indicator is embedded. (Today: typically <10%.)
- **SC-002**: The indicator deflects visibly within 100 ms of speech onset.
- **SC-003**: In every embedding location, the indicator looks visually proportionate after a single `.frame(height: X)` modifier is supplied. The three confirmed values for 0.14 are: RecordingView = 110 pt, MicrophoneTestStep = 120 pt, InputFieldView = 24 pt. No other layout configuration is required.
- **SC-004**: Zero observed cases of the indicator overflowing its container, flickering, or jittering during silence-to-speech transitions or sustained speech in QA.
- **SC-005**: Internal usability check: users no longer ask "is my mic working?" during dictation onboarding or daily use.

**Forced response language:**

- **SC-006**: In 100% of test cases where the floating-window response-language override is set to language B before the first voice turn of a new chat session, the formatted output of that first turn is produced in language B — regardless of the actual source language the user spoke. This is verified at minimum across the three most common source × target pairings used by current users.
- **SC-007**: When the resolved target language already matches the source language of the transcribed text on the first voice turn, the formatted output remains in that language with 0% spurious re-translation (i.e. the formatter does not flip languages back and forth).
- **SC-008**: On the first voice turn of a new chat session, when the floating-window override differs from the Settings default, the override wins 100% of the time.
- **SC-008a**: Follow-up voice turns within the same chat session do not carry the translation directive; the response language of follow-up turns is determined by chat continuation (existing behavior, unchanged).
- **SC-009**: After an app restart, the Settings default is restored from disk; the first opening of the floating window after restart initializes its override from this restored default.
- **SC-010**: Zero observed regressions in default formatting behaviour for users who never touch the floating-window response-language selector.

## Assumptions

- "Normal conversational volume" is interpreted as the typical microphone input level produced by a user speaking close to a built-in or external microphone in an office/home environment. The "≥50% of container height" target in SC-001 is calibrated against this; the implementer is expected to choose an amplitude mapping (e.g. non-linear / dB-scaled with appropriate gain and smoothing) that achieves this target.
- The visual style (color, shape, basic geometry) of the existing indicator is preserved. Only its size, container-relative scaling, and amplitude mapping change. Any new visual identity is explicitly out of scope (see Out of Scope).
- The existing audio level data source provides a signal of sufficient quality and update frequency to drive the redesigned amplitude mapping; no overhaul of audio capture is required.
- The set of supported response languages remains exactly what it is today. No new languages are added or removed by this feature.
- The placement of both the Settings default control and the floating-window override control remains where they are today; this feature does not move or redesign these controls.
- The existing two-stage flow (recognition then formatting) is preserved. The fix is additive: it adds an explicit translation directive to the formatting stage. The recognition stage continues to transcribe in the source language.
- The translation directive is implemented as additional language-targeting instruction inside the existing formatting-stage system prompt — the spec does not prescribe the exact wording or insertion location; only the behavior the directive must produce.
- Persistence of the Settings default uses the existing storage mechanism; this feature does not introduce a new storage location.
- The floating-window override is in-memory only (per FR-015). No new persistence mechanism is introduced.
- The mid-flow change requirement (FR-016) does not require killing or restarting an in-flight response; it only requires that the *next* submission respect the new resolved target language.
- When the formatting stage encounters transcribed text whose language is outside the supported response-language set (rare), it produces a best-effort result in the resolved target language; the spec does not mandate perfect translation in that fallback path.

## Out of Scope

- Any new visual style or redesign of the voice level indicator beyond size and amplitude scaling. (No waveform, no spectrum visualization, no color/shape change unless required to satisfy the smoothness requirement.)
- Replacing the indicator with a different visualization (e.g. waveform, spectrum, level meter with peak markers).
- Automatic detection of the user's source language from their speech (the recognition stage continues to receive its source-language signal the same way it does today).
- Adding or removing supported response languages.
- Changes to where the Settings default control or the floating-window override control are placed in the UI.
- Restructuring the two-stage pipeline; the directive is added inside stage 2, not by introducing a new stage.
- Persisting the floating-window override to disk or writing it back to the Settings default. (The override is in-memory only and re-initialized from the Settings default on every window opening — see FR-013 through FR-015.)
- Changes to the audio capture pipeline beyond what is necessary to feed the new amplitude mapping.
- Bias-changing changes to stage 1 recognition (we do not pass the target language into recognition).
- Post-hoc language detection on the formatting stage's output, automatic retry on language mismatch, and user-facing warnings about language mismatch. (Compliance with the directive is a prompt-engineering quality concern, not a runtime control-flow concern.)

## Dependencies

- Existing voice level data source — unchanged.
- Existing Settings default control and floating-window override control — unchanged in placement; this feature consumes them to compute the resolved target language at submission time.
- Existing two-stage dictation flow (recognition then formatting) — unchanged structurally; the translation directive is added inside the formatting stage.
- Existing system-prompt mechanism used by the formatting stage — extended with the translation directive; no new prompt store is introduced.
- Existing diagnostic logging system (established by spec 007) — extended with one structured event per first voice turn of a chat session, per FR-022. No new logging infrastructure is introduced.
- No new external libraries are introduced by this spec.
